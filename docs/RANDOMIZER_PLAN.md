# Built-in randomizer: implementation plan

Plan written 2026-10-20 on `feature/randomizer` (HEAD 7a5e01e). It follows the feasibility study
(`git show study/randomizer:docs/RANDOMIZER_STUDY.md`) and six read-only reports: logic, locations, asm,
tweaks, port and extras. Line numbers are from 7a5e01e. The reference is wwrando at `9775811` (VERSION
`1.10.0_9775811`, MIT), checked out read-only in `ref/wwrando`.

Agents execute this plan step by step (`R<phase>.<n>`). Every step has a goal, the files it owns, notes
on how to implement it, a verification that covers only what the step owns, and its dependencies.
Long play-throughs are not step checks; they belong to the milestone check at the end of each phase.

## Goal and scope

1. **Parity with wwrando's item randomizer at its default settings**, on the USA disc (GZLE01). A seed
   made by SwitchWaker places the same item in the same location as wwrando 1.10.0_9775811 does for the
   same seed and options (see D1).
2. **Then the main options:** progression categories, logic difficulty, key-lunacy, sword modes,
   starting gear and extra starting items, trap chests, hints (fishmen, Ho Ho, KoRL, Savage Labyrinth,
   Big Octo fairy), charts, starting island, required bosses and entrance rando.
3. **Last:** inter-dungeon warp pots, enemy palettes, enemy rando, cosmetics and the European disc.

Fixed constraints:
- The player has only the NRO and an unmodified disc. `main.dol` and the RELs are SHA-1 checked, so
  nothing is patched on disc:
  - wwrando's data edits are applied in memory after an archive loads;
  - its asm patches become `pc_rando()`-guarded changes in the decompiled functions;
  - its seed generator is ported to C++ and runs on the console.
- **A file that is not randomized behaves exactly like the original game.** Every hunk in `game/` takes
  its original branch when `pc_rando()` is 0, the same rule as `docs/QOL_PLAN.md` "Rules".
- The placement is stored per save slot, next to the save. The spoiler log is written to the SD card,
  or to the user folder on Mac.

Out of scope: music rando (unfinished upstream), custom player models, and permalinks compatible with
official `do_not_generate_spoiler_log` seeds (their `SEED_KEY` is private).

## Corrections to the study

The study's phase 1 says "assumed fill". That is wrong: wwrando does a **weighted forward fill**, and only
non-key-lunacy dungeon items are pre-placed assumed-fill style. There is also no "race mode" at this
commit; Required Bosses replaced it. The phases below replace the study's phase table.

## Decisions (each with the default we adopt)

| # | Decision | Adopted default |
|---|---|---|
| D1 | Compatibility with wwrando seeds | **Exact.** Port Python's `random` (MT19937, `init_by_array`, `getrandbits`, `_randbelow`, `choice`, `shuffle`, `sample`) and keep every Python list order and mutation (`list.remove`/append, the reordering caused by usefulness probes). This covers items, charts, required bosses, extra starting items and entrances. Permalinks use wwrando's format with the version string `1.10.0_9775811`. **Hints are checked for validity only, not byte equality**, because `hints.py` iterates Python `set`s of strings whose order depends on hash seeding. |
| D2 | `do_not_generate_spoiler_log` | Supported, with the port's own constant key (`SWITCHWAKER_SEED_KEY` in the generator). These seeds are not compatible with official ones; the UI says so. |
| D3 | Where the slot's seed is stored | A fixed 0x50-byte record in `dSv_reserve_c::mReserve` (`d_save.h:731`), which is saved and copied with the slot and read by no vanilla code. It holds the magic `"WWR1"`, a format version, a 16-byte hash and flags. The full placement goes in a sidecar file **next to the save**: `<card dir>/switchwaker-rando-<hash32>.json`. The card dir is `<userPath>/USA/Card A/`; the GCI loader ignores files that do not end in `.gci`. The sidecar is keyed by hash, not by slot, so copy and erase need no file-select hooks. Orphan sidecars are cleaned by a menu action. |
| D4 | Stale reserve on New Game | `dSv_save_c::init` does not clear `mReserve`. The new-game hook clears it **only if it holds a rando record**. In a vanilla game that never happens, so vanilla bytes are unchanged. |
| D5 | Where logs go | `<userPath>/rando/` (Switch: `sdmc:/switch/switchwaker/native/user/rando/`). Files: `WW Random <seed> - Spoiler Log.txt`, `- Non-Spoiler Log.txt`, `- Error Log.txt`, in wwrando's exact format, plus one trailing line `Generated by SwitchWaker <version>`. |
| D6 | When the seed is generated | In the options menu ("Generate seed"), on a worker thread with a progress line. The result is a *pending seed*, shown with its hash, which the next New Game consumes. File select is not hooked (revised by Phase R8: an optional "Normal / Randomizer" choice on New Game). |
| D7 | Where `pc_rando()` becomes true | When a slot whose reserve holds a valid record is loaded (`FileSelectMainNormal` after `card_to_memory`, `d_s_name.cpp:1228`). Also at New Game with a pending seed (`NameInMain`, `d_s_name.cpp:1384`), and in a debug boot with `COS_RANDO_PLACEMENT=<json>` (`pcBootStage`, `pc_logo_hooks.cpp:137`). It becomes false again at the title and at file select. Item tables patched at activation are restored from a snapshot when it turns off. |
| D8 | Archive data hook | One hook at the end of `dRes_info_c::loadResource` (`d_resorce.cpp:144`). At that point `stage.dzs`, `room.dzr` and `event_list.dat` are still raw big-endian bytes. The directory is recorded in `dRes_info_c::set` (`:56`), so `majroom`, `ma2room` and `ma3room` are told apart. Grown files (added entities) are a copy on the archive heap that replaces the `mRes[i]` slot. |
| D9 | Location fingerprints | Each patched record carries the 8-byte actor name and the vanilla item byte. On a mismatch (for example replaced content files, as in HD issue #42), log it and leave that location vanilla. |
| D10 | Messages | An overlay table checked in `fopMsgM_msgGet_c::getMesgEntry`/`getMessage` and `fopMsgM_itemMsgGet_c::getMesgEntry`/`getMessage` (`f_op_msg_mng.cpp:1508/1524/1584/1599`). The BMG is not rebuilt; the JMessage/STB path never shows randomized text. Word wrap runs at runtime with the loaded font's glyph widths, which also works for EUR later. |
| D11 | Logic data in the build | An offline converter (`native/tools/rando/gen_rando_data.py`, which uses ruamel in a Mac-only venv) writes checked-in `.inc` tables under `native/src/pc/features/rando/generated/`. The build never needs Python. Regenerating is a step-owned action, verified by a diff. |
| D12 | wwrando assets (Vscroll.arc, BTI textures) | None are shipped; the player needs only the disc. Hurricane Spin's field model reuses the song note resource (item 0x22). The texture swaps (swift sail, key bag icon, dark wood chest) are skipped until R7.5. |
| D13 | SwOp actor | Rewritten from the parameter spec (no source; `powerpc-eabi-objdump` is not installed). It is checked by behaviour on its 3 default uses. Disassembling `ref/wwrando/asm/d_a_switch_op.rel` is optional, if devkitPPC is installed later. |
| D14 | QoL features that wwrando also has | Vanilla bug fixes (QoL item 15 and the 8 newer ones) are **forced on** under rando: `pc_rando() \|\| pc_qol(X)`. Option-backed tweaks (swift sail, instant text, reveal sea chart) follow the **seed's** option: `pc_rando() ? cfg.opt : pc_qol(X)`. Speed tweaks wwrando always applies (roll, blocks, grapple, climb) are forced on. |
| D15 | Generated seed hash display | Shown in the menu and on the file-select info panel. Message 40 (name entry) is not changed. |
| D16 | Region | USA only until R7.6. On a EUR disc the rando tab is shown disabled with a reason. |
| D17 | Event bits wwrando reuses | 0x6901-0x6980 and 0x6A01-0x6A40 must stay unused by vanilla and port code. R0.1's census checks this. |
| D18 | Enemy rando | Last, labelled experimental, as upstream (`hidden=True, unbeatable=True`). |

## Conventions every step follows

**Code layout**
- New code goes in `native/src/pc/features/rando/`. Files must be named `pc_rando_*.cpp`: the
  `GLOB_RECURSE pc_*.cpp` in `native/cmake/executable.cmake:25` picks them up with no list to edit.
- Public C API: `native/include/pc/pc_rando.h`. Hook bodies of more than a few lines go in
  `native/src/pc/game_hooks/pc_rando_hooks_<area>.cpp`, declared in `native/include/pc/pc_rando_hooks.h`,
  one section per step.
- The generator (`pc_rando_gen_*`, `pc_rando_logic_*`, `pc_rando_rng*`, `pc_rando_options*`) is pure C++
  with no game headers, so unit tests and the Mac CLI can link it.

**Hunks in `game/`**
- Follow `docs/GAME_CODE_ORGANIZATION.md:11-18`: smallest `#if TARGET_PC` hunk, no renames or
  reformatting.
- Use one of three forms:
  - `pc_rando() ? new : original`;
  - `pc_rando() || original`;
  - `#if TARGET_PC` with `if (pc_rando()) {new} else {original}` and the original in `#else`.
- Mark every hunk `// pc_rando(<step>): <wwrando ref, e.g. flexible_item_locations.asm d_a_bigelf
  0x217C>; original: <value>`.
- Item ID sites use `pc_rando_loc_item(PCR_LOC_<name>, vanilla)`, which returns `vanilla` when
  `!pc_rando()`.

**Hook log**
- Each step appends its hunks to **`docs/RANDO_HOOKS.md`**, in its own section `## <step>`: file,
  function, guard form, wwrando reference.
- `docs/GAME_DIVERGENCE.md` is generated (`python3 -I native/tools/divergence_census.py`) and is not
  edited by hand. Steps run the census locally to make sure "unguarded code divergence" does not grow.
  The integrator regenerates and commits it once per wave, so parallel steps do not conflict.
- `native/tools/rando_hook_census.py` (R0.1) checks two things: every `pc_rando(` marker in `game/` is
  listed in `RANDO_HOOKS.md` and sits inside a guard, and D17 holds.

**Tests, conflict-free for parallel work**
- Unit tests: one file per step, `native/check/rando/test_<step>.cpp`. Each file builds its own
  executable `cos_rando_test_<step>` (a glob added in R0.1). It prints `ok`; `regress.sh` runs them all.
  Fixtures go in `native/check/rando/fixtures/`. They are produced by the oracle from wwrando's MIT data,
  never disc bytes.
- In-game smokes: one generic smoke `rando`, registered once by R0.1 in `kSmokes[]`
  (`pc_smoke.cpp:310`) and the frame list (`pc_frame.cpp:1703-1740`). It dispatches on
  `COS_RANDO_SMOKE=<name>` to functions listed in `native/src/pc/harness/smokes/pc_rando_smokes.def`.
  Each step appends one X-macro line there (append-only; keep both lines on a merge) and owns
  `native/src/pc/harness/smokes/pc_rando_smoke_<name>.cpp`.
- Regression lines: each step owns `native/check/regress_rando/<step>.txt`, in the format of
  `regress_targets.txt`. R0.1 makes `regress.sh` read that folder.
- Mac checks use `native/tools/run.sh <target> --stage ... --env ...` (exit 0 reached, 1 check failed).

**Steps and commits**
- One commit per verified step (memory "commit after each step"). Push only after user review.
- Work on `feature/randomizer`; parallel agents use worktrees branched from it, and their branches are
  merged back per wave.

## The oracle (Mac only)

These Python tools live in `native/tools/rando/`. The working prototypes are in the study scratchpad
(`/private/tmp/claude-501/-Users-kevin-Documents-windwaker/59322107-c59b-479e-a215-256002c6628a/scratchpad/{ww_export,ww_verify,ww_trace}.py`)
and are copied into the repo by R0.4. If the scratchpad is gone, rewrite them from the spec in R0.4.

- **`ww_export.py <seed> <out.json> [opt=json ...]`**: runs wwrando `--dry` and writes the golden
  placement. Schema `format 1`:
  ```
  {format, seed, permalink, options, extra_starting_items, charts, required_boss_locations,
   entrances, starting_island_room, locations{loc: item}}
  ```
  Our generator writes the same schema (R0.6), plus `hints` and `version` fields that wwrando ignores.
- **`ww_verify.py <placement.json>`**: rebuilds a dry `WWRandomizer` with the JSON's options and
  restores its non-item decisions (charts, required bosses via a stub `sample`, entrances, extra
  starting items). It then checks:
  - all 320 locations are filled;
  - the pool multiset is placed;
  - `check_item_valid_in_location` holds for every pair;
  - there are at least N copies of each progress item in progress-eligible, non-banned locations;
  - a reachability fixpoint reaches `Can Reach and Defeat Ganondorf` and every non-banned progress
    location.

  Exit 0 is OK, 1 is invalid; diagnostics are printed as JSON. Entrance structure (nesting, safety
  entrance) gets its own checker in R6.14.
- **`ww_trace.py <seed> [opts]`**: logs every `_randbelow(n) -> r` per randomizer. With
  `COS_RANDO_TRACE=1`, our generator writes the same format, so the first diverging call can be found.
- **`check_seeds.py --cli <cos_rando_cli> --n N --preset P [--golden]`** (R1.6): generates N seeds with
  our CLI, verifies each with `ww_verify.py`, and with `--golden` also requires byte-identical
  `locations` against `ww_export.py`.
- **`setup_oracle.sh`**: creates the venv `build/rando-venv` (ruamel.yaml 0.19.1, numpy, pillow,
  imagequant, appdirs, tqdm) and clones gclib at `d9322523` into `build/rando-deps/gclib`, because the
  `ref/wwrando/gclib` submodule is empty. Tools run with `PYTHONPATH=build/rando-deps/gclib:ref/wwrando`
  and `python -I`.

## The location sweep (Mac)

`native/tools/rando/location_sweep.py` (R2.12) runs `run.sh rando --env COS_RANDO_SMOKE=loc` once per
location, or once per stage for batches. It uses a placement JSON and the location's warp target
(stage:room:point:layer plus required event bits, from the generated key table and
`native/tools/rando/sweep_targets.json`). Each location is checked at one or two tiers:

- **T1, static (all 320):** after the stage loads, the patched record holds the placed item and a live
  actor exists with that parameter. For code locations, the smoke calls the hooked lookup and checks the
  value the decompiled function will use.
- **T2, given (chests, field items, salvage, events, boss items):**
  - chests: open with a driven pad, as `smokes/pc_chest.cpp` does;
  - field items: put the player on the item;
  - events: start the event the way `sweeps/pc_event_sweep.cpp` does;
  - boss items: spawn `Bitem`.

  The check is that `dComIfGp_event_getGtItm()` or the item-get log equals the placed item and that its
  `item_func` ran.

NPC gifts that need a whole minigame are T1 only, plus the manual checklist of the milestone
play-through. Standard placements: `identity` (vanilla items; must behave exactly as vanilla), `rotation`
(`make_test_placement.py`: every location gets a valid item of another class, covering every item ID
class), and three real `ww_export` seeds.

**R0.2 Python-compatible RNG and MD5.** *Deps: R0.1. Parallel.*
- **Owns:**
  - `features/rando/pc_rando_rng.{h,cpp}`
  - `native/tools/rando/gen_rng_vectors.py`
  - `native/check/rando/test_R0_2.cpp` and its fixture
- **Notes:**
  - MT19937 plus `init_by_array`. The key is abs(int) as little-endian u32 words trimmed to `bit_length`, so an md5 with zero top words gives fewer words.
  - `getrandbits(k)`: k ≤ 32 is `genrand >> (32-k)`; k > 32 uses `ceil(k/32)` words; k = 0 consumes nothing.
  - `_randbelow` rejection-samples with `getrandbits(n.bit_length())`. `choice` on a 1-element list still consumes.
  - `shuffle` (i from len-1 down to 1), `sample` (pool vs set, threshold `21 + 4**ceil(log4(3k))` for k > 5), `randint`, `weighted_choice` (`sample(range(total),1)` plus bisect).
  - `get_new_rng(seed, opts)`:
    - md5 of the sanitized seed (`-_'%.` plus alphanumerics, max 42 characters), plus the key from D2 when no spoiler log;
    - warm-up: for i over the 11 `RNG_CHANGING_OPTIONS` in order, for j in 1..98+i, `getrandbits(value + 20*i + j)` (bools are 0 or 1).
  - Start from the prototype `scratchpad/mt/pyrand.cpp`.
- **Verify:** vectors from CPython (seeds TestSeed1, pytestseed, abc, 3304751 and a short-key seed): 1,000 outputs of each primitive, plus the full warm-up, are identical.

## Phase R1: seed generator (pure C++, checked against the oracle)

**R1.1 Requirement compiler and evaluator.** *Deps: R0.3.*
- **Owns:** `features/rando/pc_rando_logic_expr.{h,cpp}`, `native/tools/rando/gen_logic_vectors.py`, `test_R1_1.cpp` and its fixture.
- **Grammar:**
  - `expr := term (('&' term)* | ('|' term)*)`; mixing `&` and `|` at one level is an error;
  - atoms are checked in this order:
    1. `Progressive X xN`;
    2. `<DRC|FW|TotG|FF|ET|WT> Small Key xN`;
    3. `Can Access Item Location "…"`;
    4. `Option "…" (Enabled|Disabled|Is|Is Not|Contains|Does Not Contain)`;
    5. an item;
    6. a macro;
    7. `Nothing` / `Impossible`.
- **Design:** names are interned into ids; expressions compile to node arrays; `Option` leaves fold once per seed. Macro memos are `{generation, value}`, and the generation is bumped on every inventory or macro change. `set_macro` recompiles from a string at runtime.
- **Recursion guard:** a nested entrance whose outer zone is already on the stack returns true (cached); any other recursion asserts.
- **`items_needed`:** the union with max counts over **all** children, for both AND and OR, and `{}` if the expression is already satisfied.
- **Verify:** fixture of 30 random inventories × 320 locations × 4 option sets: met/not met and `items_needed` match Python.

## Phase R8: in-game New Game choice (last)

Added on 2026-10-24 at the user's request, as the final phase. It revises D6 ("File select is not hooked"): the
options and the seed stay in the port's options menu (R4.1-R4.5), but the player can also start a randomized file
from the game's own file select, without pressing "Generate" first. Configuring the options inside the game's menus
is out of scope: the J2D/BLO layouts have no lists or text fields, and wwrando has dozens of options.

**R8.1 File select "Normal / Randomizer" choice.** *Deps: R4.4, R3.20; after Milestone R7 (EUR text) or USA-only
first.*
- **Flow:** choosing an empty slot in `dFile_select_c` asks one extra Yes/No question ("Randomizer file?") before
  the name entry, reusing the existing `YesNoSelect` / `yesNoCursorMove` / `yesNoPaneMove` panes and animations
  (`game/src/d/d_file_select.cpp`). "No" is the vanilla flow, unchanged. "Yes" uses the pending seed if there is
  one, otherwise generates the seed of the current menu settings on the worker job (`pc_rando_genjob`) with a
  wait state on the panel, then continues to the name entry, which consumes it as New Game does today (R4.4).
- **Text:** the question and the seed line (name or hash, "Name1 Name2") are new messages through the R3.20
  message overlay; on EUR they follow R7.6c's language rule.
- **Errors:** a generation error shows a one-line message and returns to the slot choice; the error log is written
  as in R4.3.
- **Setting:** a menu row "Ask on New Game" (default on once R8.1 ships; off restores the D6 behaviour exactly).
- **Owns:** marked, guarded hunks in `d_file_select.cpp` (new state in the move table, the empty-slot branch);
  `game_hooks/pc_rando_hooks_fileselect_newgame.cpp`; one row in `pc_rando_menu.cpp`; smoke `fsnewgame`;
  `regress_rando/R8.1.txt`.
- **Risks:** the panes' animation code is decompiled and driven by `g_fsHIO` values, so the new state must reuse
